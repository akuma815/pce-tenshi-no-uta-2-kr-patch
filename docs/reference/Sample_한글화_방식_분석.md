# Sample 한글화 사례 분석 — 천사의 시 II 적용 가능성 검토

분석일: 2026-07-12
대상: `Sample/track02.bin`(원본) vs `Sample/track02_Patched.bin`(한글 패치본)
목적: 이미 성공한 다른 PCE-CD 게임 한글 패치의 **방식**을 역분석하고, 그 방식을
천사의 시 II에 그대로 적용할 수 있는지 판정.

---

## 1. Sample 파일 개요

| 항목 | 값 |
| --- | --- |
| 크기 | 24,399,648 B (원본·패치 동일) |
| 포맷 | RAW 2352 B/섹터 Mode1, 10,374섹터 단일 데이터 트랙 이미지 |
| 리드인 | 앞 75섹터는 제로 프리갭, 첫 sync는 물리섹터 75 |
| 게임 정체 | **허드슨 PCE-CD 게임** — IPL 헤더(`PC Engine CD-ROM SYSTEM` / `Copyright HUDSON` / `NEC Home`)가 데이터 상대 섹터 150~151에 존재. 천사의 시 II와 **동일한 부트 구조** |

> 이하 "drel"(data-relative) = 물리섹터 − 75. 유저데이터(각 섹터 [16:16+2048])만 비교.

## 2. 변경량 — 정밀 인플레이스 패치

| 지표 | 값 |
| --- | --- |
| 변경된 유저데이터 섹터 | 321 / 10,374 (**약 3%**) |
| 변경 구간 수 | 195개 (대부분 단일~수 섹터) |
| 파일 크기 변화 | **없음** (바이트 단위 동일 크기) |

전체를 재빌드한 것이 아니라, **필요한 바이트만 같은 자리에 덮어쓴** 전형적인
인플레이스 패치다. 이 점이 walkthrough.md가 재설계로 채택한 원칙(고정 크기·제자리
수정·상주 RAM 미사용)과 정확히 일치한다.

## 3. 무엇을 바꿨나 — 핵심 발견

### 3.1 변경 = "내장 폰트 글리프를 한글로 다시 그림" (제자리)

변경 구간의 바이트를 SJIS/EUC-KR/CP949/Johab로 디코딩해봤으나 **텍스트로 해석되는
변경은 단 한 건도 없었다.** 대신 전형적인 **글리프 비트맵 교체**였다.

예 — drel 866, offset 0x3f8 (원본은 한자, 패치는 한글, 둘 다 16px 폭 글리프 비트맵):

```text
ORIG  : f0 03 30 03 f0 03 c0 03 c0 03 c0 03 ...   (한자 획 패턴)
PATCH : fc 00 cc 00 fc 00 f0 00 f0 00 f0 00 ...   (한글 획 패턴)
```

- 각 글리프가 32바이트(16행 × 2바이트) 단위이며 **3~4회 복제**되어 있다
  → PCE 4비트플레인 타일에 1bpp 폰트를 각 플레인에 복사해 단색으로 표시하는 방식.
- 원본 자리에 **정확히 같은 길이**로 한글 비트맵을 덮어썼다. 코드/포인터 변화 없음.

### 3.2 폰트가 여러 군데 내장 (시스템 + 데이터)

- **시스템 폰트**: IPL 직후 drel 155~184에 집중 → 천사의 시 II의 시스템 영역
  (섹터 18~289) 폰트 배치와 대응.
- **데이터 폰트**: drel 866·874·1042 등 후반 데이터에도 동일한 글리프 교체
  → 장면/모듈별로 폰트 사본을 들고 있고 그 사본들도 각각 제자리에서 교체.

### 3.3 곁다리 변경

- drel 968·1120 등에서 FF 영역에 1바이트(`dd`, `aa`) 수정 → 미세 조정.
- 파일 끝(drel 9954~10232)의 00/FF 패딩이 일부 재기록 → 재빌드 툴의 패딩 정규화
  아티팩트로 보이며, 실제 번역 콘텐츠와 무관.

### 3.4 결정적으로: 후킹도, 상주 로더도, 사이드카도 없음

새 코드 주입(부트 훅/GETFNT 훅), CD_READ 추가 로드, 끝부분 상주 텍스트 풀 —
**어느 것도 없다.** 순수하게 "디스크에 이미 있던 글리프 그림을 한글로 바꾼" 것뿐이다.

## 4. 이 방식이 성립한 이유

Sample 게임은 **자체 글리프 폰트를 디스크에 내장**하고, 화면 텍스트를 그 폰트에서
글리프 비트맵을 뽑아 그리는 구조다. 그래서 번역이 다음과 같이 단순해진다:

1. 게임이 쓰는 글자(한자/가나)의 글리프 비트맵을 **한글 비트맵으로 덮어쓴다.**
2. 스크립트가 "코드 X번 글리프"를 그리라고 하면, 그 자리에 이제 한글이 그려진다.
3. 길이·포인터·메모리 배치가 전혀 바뀌지 않으므로 **부작용이 없다.**

즉 폰트가 **온디스크**이고 텍스트가 **고정 그리드/고정 코드** 기반이라, 제자리
repaint만으로 완결된다.

## 5. 천사의 시 II와의 구조 비교

| 항목 | Sample 게임 | 천사의 시 II |
| --- | --- | --- |
| 한자 폰트 | **디스크 내장** (덮어쓰기 가능) | **BIOS System Card ROM** (`EX_GETFNT`) — 디스크에 없음 |
| 텍스트 저장 | 글리프 코드 / 타일 기반, 고정 길이 | 가변 길이 혼합 인코딩 스트림, 이벤트 바이트코드에 인라인 |
| 렌더 경로 | 내장 글리프 → 블릿 | 스트림 fetch(`$4111`) → `EX_GETFNT` → VRAM |
| 메모리 구조 | 정적/제자리 | 55개 슬롯 + 오버레이 로더, 뱅크 $68~$87 동적 소유권 |
| 번역에 필요한 것 | 폰트 비트맵 repaint | 폰트 삽입(BIOS 우회) + 스트림 리다이렉트 + 뱅크 안전성 |

두 게임은 **텍스트 렌더 아키텍처가 근본적으로 다르다.** 특히 천사의 시 II는
한자 글리프가 디스크에 없고 BIOS 폰트를 호출하므로, Sample처럼 "폰트를 덮어쓰는"
행위 자체가 불가능하다(덮어쓸 대상이 디스크에 없음). 이것이 GETFNT 후킹이라는
복잡성이 불가피한 근본 이유다.

## 6. 적용 가능성 판정

### 6.1 그대로는 적용 불가 (대사 본문)

Sample의 핵심 방식(**내장 폰트 제자리 repaint**)은 천사의 시 II의 **대사 시스템에
직접 적용할 수 없다.** 이유:

- 대사 한자는 BIOS 폰트라 덮어쓸 온디스크 글리프가 없음.
- 대사는 가변 길이 스트림이라 "고정 코드 → 고정 글리프" 치환 모델이 성립하지 않음.
- 따라서 천사의 시 II는 여전히 (a) 한글 글리프 공급(GETFNT 후킹 또는 대체 렌더),
  (b) 스트림 리다이렉트, (c) 뱅크 생존성 확보가 필요하다 — walkthrough.md의 재설계가
  옳다.

### 6.2 부분 적용 가능 (그래픽/타일 텍스트 요소)

천사의 시 II에도 **비-BIOS, 타일/그래픽 기반 텍스트**가 존재한다:

- 시스템 영역(섹터 18~289)의 **가나 폰트 타일** — Sample처럼 제자리 repaint 가능
  (단, 가나 90여 타일 공간에 한글을 다 넣을 순 없으므로 UI 한정).
- 타이틀/오프닝의 **로고·베이크된 그래픽 텍스트**, 12×12 가나 폰트 인덱스 테이블
  (섹터 123·222) 등.
- 이런 요소는 Sample 방식(고정 크기 그래픽 교체)이 그대로 유효하며, **부작용 없는
  안전한 부분**이므로 우선 적용 대상.

### 6.3 방법론적 교훈 (가장 중요)

Sample은 **"성공한 PCE-CD 한글 패치는 순수 인플레이스·고정 크기·무상주였다"**는
실증 사례다. 이는 천사의 시 II 재설계 방향을 뒷받침한다:

- 상주 RAM 예약(뱅크 $68~$87)·사이드카 상주 풀은 지양 (walkthrough.md와 일치).
- 리다이렉트는 **고정 크기**로, 이벤트 분기·인라인 파라미터가 이동하지 않게.
- 번역 데이터의 수명은 **원본 로더의 수명과 정확히 일치**하도록 슬롯/모듈에 동봉.

차이점은, Sample은 폰트가 온디스크라 스트림 리다이렉트조차 필요 없었던 반면,
천사의 시 II는 BIOS 폰트 + 스트림 구조라 **모듈-로컬 GETFNT 후킹 + 고정 크기
리다이렉트**라는 추가 계층이 불가피하다는 점이다.

## 7. 권고 (실행 순서)

1. **선(先)-저위험 적용**: Sample 방식을 천사의 시 II의 그래픽/타일 텍스트
   (타이틀, UI 가나 폰트, 로고)에 제자리 repaint로 먼저 적용해 파이프라인·검증
   루프를 확립한다. 크래시 위험이 없어 회귀 기준점을 만들기 좋다.
2. **본(本)-대사 시스템**: walkthrough.md의 모듈-로컬 후킹 + 슬롯 동봉 + 고정 크기
   리다이렉트 설계를 계속 진행한다. Sample은 이 부분을 대체하지 못한다.
3. **폰트 공급 결정**: 대사 한글은 BIOS 우회가 필요하므로, GETFNT 후킹으로 RAM
   글리프를 공급하되 **후킹/글리프를 해당 모듈 padding에 로컬 배치**(상주 뱅크 금지).
4. **검증**: Sample처럼 "원본과 스크린샷 비교, 의도한 텍스트 픽셀만 차이"를 회귀
   기준으로 삼는다(walkthrough.md 6절과 동일).

---

## 8. 한 줄 결론

Sample은 **폰트를 디스크에 내장한 게임**이라 "폰트 제자리 덮어쓰기"만으로 한글화가
끝났지만, 천사의 시 II는 **BIOS 폰트 + 가변 길이 스트림**이라 같은 방식이 대사에는
통하지 않는다. 다만 Sample은 (1) 인플레이스·고정 크기·무상주라는 **올바른 패치
원칙**을 실증하고, (2) 천사의 시 II의 **그래픽/타일 텍스트 부분에는 직접 재사용
가능**한 방식을 제공한다.
