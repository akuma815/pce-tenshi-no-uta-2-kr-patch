## 0. 요약 (결론 먼저)

1. **"반복 실패"의 근원은 단 하나 — 한글 글리프를 게임 RAM 어딘가에 두려는 시도**다.
   RAM bank 32개 전부 소유자가 있어서, 글리프 풀을 둘 곳을 찾는 싸움이 Task 0~7
   실패 전부와 Z8.9 canary 3연속 FAIL의 공통 원인이다.
2. **BIOS(시스템카드) 폰트 교체는 이 싸움 자체를 없앤다** — 글리프가 ROM에 있으므로
   게임 RAM·디스크에 글리프를 둘 필요가 없다. 그리고 이 방식의 핵심 메커니즘은
   이미 이 프로젝트에서 **인게임 런타임 PASS**를 받은 적이 있다 (2026-07-17,
   exact_substitution_probe).
3. 이 방식이 7월에 기각된 근거("index 1722 외 슬롯 교체 시 시작화면 전면 손상")를
   **오늘 5종 부팅 재실험으로 재검증한 결과, 재현되지 않았다.** 과거 판정은 오염된
   테스트 환경의 산물로 판단된다. → §3
4. 단, **BIOS 방식도 텍스트 공간 문제는 해결하지 못한다.** 번역이 원문 자리에 들어가는
   레코드는 235개 중 12개(5%)뿐이라 리다이렉트는 어느 방식이든 필요하다. → §5
5. 권고: **인게임 확인 실험 1건(약 5분)으로 BIOS 트랙을 확정**하고, 배포 조건(수정
   시스템카드 동반)에 대한 사용자 결정을 받는다. A-2 canary 게이트는 어느 트랙이든
   텍스트 공간에 필요하므로 그대로 진행한다. → §7

## 1. "반복 실패"의 실체 분해

실패로 보이는 이력을 원인별로 나누면 실제로는 세 덩어리다.

| 시기 | 실패 | 근원 |
| --- | --- | --- |
| 7/12~18 Task 0~7 | `$2B0F` 훅, `$5230` 디스패처, bank `$6D/$84` 풀, sidecar — 전부 전환 시 손상 | **글리프·코드를 게임 RAM에 상주**시키려 함 → 오버레이 소유권 침범 |
| 7/16~17 BIOS 진단 | 896/18/2글자 교체 빌드 "시작화면 손상" | **§3에서 재현 실패 — 오염된 증거로 판명** |
| 7/27~28 Z8.9 | canary 3연속 FAIL (A-1 2건, A-2 v1 1건) | **글리프+텍스트를 둘 디스크/RAM 공간 탐색**의 시행착오 (각 원인은 규명됨) |

Z4~Z8.8은 전부 PASS였다. 즉 실패는 "분석"이 아니라 일관되게 **"한글 글리프를 둘 곳"**
에서 났다. 이 관점에서 BIOS 폰트 재검토는 정확히 급소를 겨눈다.

## 2. 두 방식의 구조 비교

### A안 — 현행: 게임 소유 글리프 (Ziria 모듈 재링크)

```
번역 텍스트(커스텀 코드) ─ reader redirect 훅 ─→ 로컬 글리프 풀(RAM) ─→ 화면
                                                   ↑ A-2 로더 2차 read로 적재
일본어 fallback ──────────────────────────────→ BIOS EX_GETFNT
```
- 글리프 9,360 B + 코드표를 **family별로 게임 RAM에 적재**해야 함 → 지금까지의 모든 난관
- 원본 시스템카드 유지 (배포 조건 우위)

### B안 — BIOS 폰트 교체 (수정 시스템카드)

```
번역 텍스트(표준 SJIS 2바이트) ─→ 게임의 기존 렌더 경로 그대로 ─→ BIOS EX_GETFNT
                                                                    ↑ 한자 슬롯에 한글 글리프
```
- 게임의 모든 renderer가 이미 `EX_GETFNT`(mode 1, 12×12)를 쓰므로 **훅·글리프 로더·
  커스텀 코드표·RAM 확보가 전부 불필요**. 필드·전투·Memo·탑·초상화가 자동 커버.
- 텍스트는 재배정한 SJIS 코드로 인코딩 — Z4~Z6에서 실증된 "같은 길이 2바이트 치환"과
  동일 메커니즘.
- **인게임 실증 이력**: exact_substitution_probe (7/17 PASS) — 원본 게임 스트림의
  2바이트를 `8F6F(出)`로 치환 + 出 글리프를 `가`로 바꾼 시스템카드 → 첫 대사에서
  한글 표시, 시작화면·그래픽·페이지 전환 모두 정상.
- 비용: **배포에 수정 시스템카드 동반 필수** (절대 규칙 #6과 충돌 — 사용자 결정 필요)

### 3.3 시스템카드 mode-1 폰트 실측 지도 (오늘 확정)

- 공식: `ROM 0x30000 + compact_index × 18` (12×12 1bpp, 2행=3바이트 팩,
  EX_GETFNT가 18→32 B 확장). 공식 소유: `tools/analyze_system_card_font_slots.py`
- 슬롯 구성 (총 3,640):

| 구간 | 슬롯 | 내용 |
| --- | --- | --- |
| 0 | 1 | 00 채움 |
| 1~3417 | 3,417 | **실존 글리프** (가나·기호·한자) — 여기가 교체 대상 |
| 3418~3567 | 150 | FF 채움 — 과거 18글자 probe가 쓴 곳. 부트는 무해 확인, 그래도 실존 슬롯 우선 |
| 3568~3639 | 72 | 후행 데이터 (글리프 아님 추정) — 사용 금지 |

- **필요 1,053자 vs 가용 ~3,417슬롯** — 3배 여유. 시스템카드 자체 UI(백업 관리 화면
  등)가 쓰는 글리프만 회피하면 된다 (§7 실험 2에서 확인).
- 896슬롯 진단 빌드의 실제 diff는 mode-0 공식(`0x10000+idx×32`)으로 **0x1E6C0 등
  0x30000 미만 영역**에 썼다 — mode-1 폰트와 무관한 위치였음도 오늘 실측으로 확인.

## 4. 어느 방식이든 남는 문제 — 텍스트 공간

field 235레코드 실측 (원문 = 토큰 압축 스트림, 번역 = 2 B/글자 + NUL):

| 지표 | 값 |
| --- | --- |
| 제자리 적합 (번역 ≤ 원문 자리) | **12개 (5%)** |
| 초과 | 223개 (95%), 부족 합계 2,746 B (중앙값 +9 B, 최대 +85 B) |
| 원문 총량 / 번역 총량 | 14,816 B / 17,535 B |

→ **고정길이 제자리 전략만으로는 불가.** Sample 게임(다른 게임, 코드 교차검색 0건으로
오늘 확정)이 제자리 repaint만으로 끝난 것은 폰트·텍스트가 모두 온디스크 고정 구조였기
때문이고, 이 게임은 텍스트가 이벤트 바이트코드에 인라인이라 늘릴 수 없다.
따라서 **wire v2 리다이렉트(index+텍스트를 별도 공간에 두고 reader가 전환)는 B안에서도
필요**하며, A-2에서 만든 인프라(로더 훅, LBA 풀, source key 산식)가 그대로 재사용된다.

공간 수지 비교:

| 항목 | A안 (현행) | B안 (BIOS) |
| --- | ---: | ---: |
| index | 2,852 B | 2,852 B |
| 번역 텍스트 | 14,640 B | ~14,640 B (SJIS 인코딩, dedup 동일) |
| 글리프 | 9,360 B | **0 B (ROM)** |
| 합계 | 26,852 B | **~17,492 B (-35%)** |
| A-2 풀 요구 | 14섹터 | **9섹터** |
| 게임 측 신규 코드 | redirect 훅 + 글리프 적재/코드표 | **redirect 훅만** |
| Z9 확대(renderer 7종) | family별 글리프 패키지 각각 | **자동 커버** (전 renderer가 같은 GETFNT) |

## 5. 기타 검토안

- **C. 부분 제자리 repaint (Sample 방식)**: 타이틀·UI 등 온디스크 타일 텍스트에는
  어느 트랙이든 그대로 유효. A/B와 병행하는 보조 수단이지 대안이 아님.
- **D. Arcade Card 요구 (RAM 2 MB)**: 글리프·텍스트를 AC RAM에 — 공간 문제는 소멸
  하나 포트 접근 코드 신규 작성 + 실기·에뮬 요구사양 상승. B안이 같은 이득을 더 싸게
  얻으므로 후순위 참고로만 기록.
- **E. 1바이트 토큰 사전 재활용**: 원문 압축 사전을 한글 고빈도 음절로 재배정하면
  텍스트가 원문 수준으로 압축돼 제자리 적합률이 급상승할 수 있음 — 사전 위치·소비
  코드 분석이 선행돼야 하므로 B안 확정 후의 최적화 항목.

## 6. B안의 리스크 정리

| 리스크 | 평가 |
| --- | --- |
| 배포에 수정 시스템카드 필수 | **구조적 비용. 사용자 결정 사항** (§8). 원본 카드 대비 xdelta로 배포하면 저작물 재배포 회피 |
| 실기 구동 | 커스텀 카드 롬 구동 수단(에버드라이브/SSDS3 등) 필요 |
| 패치 카드로 다른 게임 구동 시 | 그 게임의 해당 한자가 한글로 표시됨 — "이 게임 전용 카드"로 안내 |
| 시스템카드 자체 화면(백업 관리)의 한자 슬롯 | 해당 슬롯 회피 필요 — 실험 2로 목록화 |
| 인게임 재검증 미완 | 실험 1로 해소 (부트는 금일 5종 검증 완료, 과거 인게임 PASS 이력 존재) |
| 12×12 한글 가독성 | one_glyph 때 "가가 기처럼 보임" — Galmuri 렌더 파라미터 조정 필요 (품질 작업, 위험 아님) |
