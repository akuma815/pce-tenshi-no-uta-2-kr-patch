진행 내용 5
원본 부트 프로그램은 실행되면 맨 처음 주소 $4000에서 복귀하여 $600B에 위치한 내부 초기화 루틴으로 점프(JMP $600B)하도록 설계되어 있습니다.
이 초기화 루틴($600B)은 비디오/사운드 장치 설정, CD-ROM 제어기 초기화 및 실제 메인 게임 엔진 코드를 디스크에서 읽어 들이는 핵심 처리를 수행한 후, 비로소 $9E5E로 점프하여 게임을 구동시킵니다.
하지만 기존에 구성되어 있던 우리의 부트 훅 코드는 한글 폰트를 다 읽고 난 뒤, 초기화 루틴을 전부 생략한 채 곧바로 최종 단계인 **JMP $9E5E**로 뛰어넘어 버렸습니다.
이로 인해 CD-ROM 초기화 루틴이 수행되지 않은 채 게임 엔진 시작 주소로 강제 점프하면서 가상 디스크 드라이버가 다시 먹통이 되어 JUST A MOMENT... 화면에서 응답하지 않았던 것이었습니다.

부트 로더 훅 파일의 마지막 리턴 점프 벡터를 $9E5E에서 원본 초기화 주소인 $600B(0x4C, 0x0B, 0x60)로 올바르게 수정하였습니다.
이로써 폰트/스크립트 28섹터 로딩이 끝나면 원본 게임의 데이터 로드 루프 및 CD 초기화 루틴($600B)이 정상 순서대로 가동된 다음 자연스럽게 최종 게임 엔진으로 연계됩니다.


진행 내용 6
PC Engine CD BIOS의 데이터 읽기(CD_READ, $E009) 함수를 Mode 6(연속 뱅크 단위 로드)으로 호출할 때, **$FB 레지스터(주소의 High Byte 및 오프셋 지정용)**가 명시적으로 초기화되어야 합니다.
원본 슬롯 로더 코드를 확인해 보니, $FF에 모드 6을 설정하기 바로 전에 STZ $FB (주소 상위 바이트 레지스터를 0으로 강제 클리어) 지시어를 실행하고 있었습니다.
기존 부트 훅에서는 $FB 레지스터의 초기화를 빠뜨렸는데, 이로 인해 BIOS 내부에서 주소 계산이 어긋나 엉뚱한 LBA 혹은 비정상적인 메모리 로딩이 유발되면서 에뮬레이터 에러(Unsupported scenario/unhandled sector type)가 연쇄 발생한 것으로 파악되었습니다.
부트 로더 훅 코드에 0x64, 0xFB (STZ $FB) 인스트럭션을 추가하여 BIOS 호출 규격을 완벽하게 맞추었습니다.


진행 내용 7
PC Engine CD BIOS의 데이터 읽기(CD_READ, $E009) 함수를 Mode 6(연속 뱅크 로드)으로 호출하여 데이터를 읽어 들일 때, BIOS는 디스크 파일 데이터를 기록하기 위해 대상 물리 RAM 뱅크들(우리의 경우 $81–$87)을 CPU의 논리 주소창인 MPR2(주소 $4000–$5FFF) 및 MPR3(주소 $6000–$7FFF) 영역에 임시로 맵 바인딩하게 됩니다.
하지만 이 시점에 CPU가 실행 중이던 우리의 부트 로더 훅 역시 $4000 영역(MPR2)에 로드되어 돌아가고 있었습니다.
따라서 JSR $E009를 호출하는 순간, 데이터가 뱅크에 쓰이면서 CPU가 현재 실행하고 있던 코드 창 자체가 날아가고 폰트 데이터/텍스트 데이터로 강제 덮어씌워지게(MPR 매핑 강제 전환) 됩니다.
결국 CD_READ 함수가 끝나고 코드로 복귀하는 주소(RTS)가 원래의 훅 코드가 아니라 폰트 데이터 한가운데로 떨어지면서 CPU가 폰트 픽셀 데이터를 바이너리 코드로 오인해 무작위 명령어를 실행하다가 엉뚱한 SCSI LBA 명령을 날려 에뮬레이터에서 unhandled sector type 예외가 발생하고 뻗었던 것이었습니다.

완벽한 아키텍처적 조치 (Work RAM 구동형 로더 스텁 도입)
CD_READ 도중 실행 중인 코드가 소실되는 현상을 막기 위해, 읽기 명령을 절대로 맵 전환에 영향을 받지 않는 Work RAM 영역에서 안전하게 실행하도록 아키텍처를 전면 개선했습니다.

Work RAM 스텁 복사: 부트 프로그램이 시작되면, $4010에 위치한 최초 진입 코드가 51바이트 크기의 초경량 디스크 로더 스텁을 **Work RAM 영역인 $2100**으로 먼저 복사한 후 $2100으로 점프합니다.
안전한 CD 읽기: Work RAM인 $2100 영역(MPR1)은 CD_READ 도중에 매핑이 바뀌지 않는 유일하게 안전한 RAM 공간입니다. 이곳에서 안심하고 LBA 6052로부터 한글 데이터 28섹터를 읽어 들입니다.
논리 뱅크 맵 복구: 로딩이 완료되면 즉시 원래 부트 프로그램이 있던 물리 뱅크 $02와 $03을 각각 MPR2($4000–$5FFF) 및 MPR3($6000–$7FFF) 영역에 다시 매핑하여 원상 복구합니다.
연계 동작: 원상 복구되어 정상화된 $4100에서 훅 코드들을 Work RAM $2200으로 안전하게 복사하고, 최종적으로 원본 게임 진입점인 $600B로 깨끗하게 점프합니다.


진행 내용 8
예외가 발생한 VDC.UpdatePatternData 및 RunDmaForScanline은 에뮬레이터가 VRAM(비디오 램)으로 폰트나 스프라이트 같은 그래픽 패턴 데이터를 전송(DMA)하는 시점에 호출됩니다.
PC Engine CD BIOS의 폰트 획득 서비스(EX_GETFNT) 호출 시, 게임 엔진은 호출 직전의 Y 레지스터 및 X 레지스터 값이 호출 후에도 그대로 보존될 것을 기대하고 작업을 수행합니다.
하지만 우리의 커스텀 한글 폰트를 32바이트씩 루프로 복사하는 getfnt_hook 코드 내에서 Y 레지스터를 인덱스 카운터로 마구 조작한 후 원상 복구(PLY 등)해주지 않았습니다.
이로 인해 EX_GETFNT가 완료되어 게임 엔진으로 복귀했을 때 Y 레지스터 값이 32로 오염되어 있었고, 엔진은 오염된 레지스터로 VRAM 대상 주소 계산 및 DMA 전송 크기를 엉뚱하게 계산하여 범위 초과(IndexOutOfRangeException) 예외를 발생시키며 크래시가 났던 것입니다.

getfnt_hook 내부에서 실제 한글 폰트 주소를 계산하고 32바이트 복사 루프를 돌기 전, **PHY (0x5A) 및 PHX (0xDA)**를 사용해 기존의 Y 및 X 레지스터 값을 스택에 안전하게 백업해 둡니다.
복사 루프가 끝난 후, 복귀하기 직전에 **PLX (0xFA) 및 PLY (0x7A)**를 사용해 스택에서 원본 레지스터 값을 고스란히 복구하여 리턴하도록 수정했습니다.
또한, 훅 코드가 약간 늘어남에 따라 부트 로더 훅에서 메모리 영역 복사 시의 카운터 크기도 정확히 228바이트(LDY #227 / 0xE3)로 맞춤 조정했습니다.


진행 내용 9
규약 분석: PC Engine CD BIOS의 EX_GETFNT($E060) 함수는 폰트 픽셀 데이터를 호출자가 제공한 버퍼 주소($FA/$FB)로 복사(Copy)해 주는 함수가 아닙니다.
리턴 동작: 이 함수는 입력된 문자 코드($F8/$F9)에 해당하는 폰트가 위치한 BIOS ROM(MPR3 영역) 내의 논리 메모리 포인터 주소를 $F8/$F9에 담아 반환하는 방식으로 동작합니다. 그러면 호출한 게임 엔진측에서 반환된 $F8/$F9 주소에서 루프를 돌며 필요한 바이트만큼을 직접 읽어 VRAM으로 보냅니다.
기존 코드의 문제점: 기존의 훅 코드는 우리가 임의로 지정한 $FA 주소로 데이터를 마구잡이로 복사한 뒤, $F8/$F9 리턴 주소는 원본 캐릭터 코드(예: $EB01)인 상태 그대로 방치해 두고 리턴했습니다.
연쇄 크래시: 이 때문에 게임 엔진은 $EB01을 실제 폰트 데이터가 든 메모리 주소로 인식하고 이 영역의 임의의 쓰레기 값을 읽어 VRAM 주소 레지스터 및 그래픽 데이터로 전송했습니다. 결국 이상한 값이 VDC(비디오 컨트롤러) 주소 레지스터로 흘러 들어가면서 UpdatePatternData에서 유효 범위를 벗어난 VRAM 메모리 주소 접근으로 인식되어 에뮬레이터 에러(IndexOutOfRangeException)가 났던 것입니다.

복사 루프를 제거하고 BIOS 규약에 맞춰 반환값 포인터를 올바르게 반환하도록 수정했습니다.

포인터 반환: 훅 코드 내에서 커스텀 한글 폰트가 적재된 물리 뱅크를 MPR3($6000–$7FFF)에 매핑한 뒤, 폰트의 실제 주소 계산 결과값을 $F8(Low Byte) 및 $F9(High Byte) 레지스터에 직접 대입합니다.
복사 제거 및 복구: 훅 자체에서 데이터를 복사하는 오버헤드(copy_loop)를 전부 걷어냈으며, 호출한 게임 엔진이 복사 작업을 정상 수행할 수 있도록 매핑한 MPR3 물리 뱅크를 강제로 원상 복구하지 않고 그대로 리턴하도록 설계했습니다. (호출자 측에서 복사가 끝난 후 자체적으로 복구합니다.)
최적화 및 정렬: 코드가 훨씬 가벼워졌으며(45바이트), 부트 로더 훅의 메모리 복사 바이트 수 카운터도 정확히 207바이트(LDY #206 / 0xCE)로 안전하게 재조정했습니다.

진행 내용 10
이전 단계에서 우리는 폰트 복사 과정 없이 포인터만 $F8/$F9에 넘겨준 다음, 매핑했던 폰트 뱅크를 복구하지 않고 그대로 남겨둔 채 리턴했습니다.
이로 인해 호출한 곳으로 돌아갔을 때 호출자는 돌려받은 $F8/$F9 주소에서 한글 폰트를 정상적으로 복사는 하지만, 그 이후 게임 코드가 실행되는 과정에서 MPR3 영역에 원래 들어있었어야 할 게임 데이터 뱅크가 아닌 폰트 뱅크가 그대로 물려 있는 상황이 벌어졌습니다.
결국 복사가 끝난 뒤 게임 코드가 MPR3의 뱅크 데이터(예: VRAM 전송 주소 및 기타 게임 설정 테이블)를 읽으려고 할 때 폰트 픽셀을 데이터로 읽게 되며 다시 쓰레기 VRAM 주소를 발생시켰고, 결과적으로 똑같은 VDC IndexOutOfRangeException 예외가 발생한 것이었습니다.

폰트 데이터를 Work RAM 버퍼로 복사: 폰트 조회 호출이 감지되면 폰트가 들어 있는 뱅크를 MPR3에 임시 매핑한 다음, 32바이트 한글 폰트 데이터를 **Work RAM 영역 내 안전한 유휴 주소 공간인 $21E0–$21FF**로 직접 1차 복사합니다.
논리 뱅크 매핑 즉시 원상 복구: 복사가 끝나면 MPR3의 물리 뱅크 매핑을 원래 호출 직전 상태(예: $03)로 즉시 완벽하게 복구합니다.
상시 접근 가능한 포인터 반환: 복구된 상태에서 $F8/$F9가 복사된 임시 버퍼 주소인 **$21E0**을 가리키도록 설정하고 리턴합니다.
결과: 호출한 게임 엔진은 언제나 접근 가능한 안전한 Work RAM 주소($21E0)에서 데이터를 문제없이 퍼가며, 동시에 게임이 작동하는 코드 영역 매핑도 완벽하게 살아있게 됩니다.


진행 내용 11 (Claude 진단, 2026-07-12)
== 치명적 근본원인: fetch hook 옵코드 손상 (게임이 아예 안 돌던 진짜 이유) ==
실제 patched.bin을 역어셈블해보니 부트 프로그램 $4100의 fetch hook 마스터가 손상돼 있었습니다.
patch_iso.py build_fetch_hook()에서 분기 오프셋을 조정하려다 `hook[9] = 0x33`을 대입했는데,
index 9는 BNE의 "옵코드(0xD0)" 자리이고 조정해야 할 "오프셋"은 index 10이었습니다.
그 결과 `CMP #$01 / BNE done`(C9 01 D0 13)이 `C9 01 / 33 13 ...`로 깨졌고,
0x33 = TAM #$13 (A값을 MPR0/MPR1/MPR4에 뱅크 매핑)이 실행되면서, 텍스트 첫 바이트를 fetch하는
순간 제로페이지/스택/Work RAM($2000, 훅 코드 자신이 있는 MPR1 포함) 매핑이 통째로 날아가
즉시 폭주했습니다. 점프테이블 $4033→$2200 패치가 적용돼 있으므로 모든 대사 fetch가 이 훅을
지나가 → 오프닝/첫 대사에서 바로 크래시. 이것이 "정상 실행 안 됨"의 직접 원인입니다.

조치: patch_iso.py를 `hook[9]=0xD0`(BNE 옵코드 유지) + `hook[10]=(done_off - 11)`(동적 계산,
현재 0x32)로 수정. 현재 patched.bin에는 마스터 fetch hook($4100)을 올바른 62바이트로 직접
재기록해 즉시 테스트 가능하게 함(부트 훅이 런타임에 $2200으로 복사하므로 마스터만 고치면 됨).
수정 후 역어셈블 정상 확인: 4109: D0 32 BNE $413D.

== getfnt hook은 "copy-to-$FA"가 맞음 (진행 내용 9/10의 전제는 오류) ==
현재 patched.bin의 getfnt hook은 진행 내용 9/10에서 바꿨다는 "$21E0 포인터 반환/복사 제거" 방식이
아니라 옛 "글리프 32바이트를 ($FA)로 복사" 방식이었습니다. 그런데 실제 렌더러를 역어셈블해보니
이 방식이 오히려 정확합니다:
 - 필드 렌더러 $8820: 매 글자마다 $FA/$FB(=$33xx 버퍼)를 세팅 → JSR $8845(내부 GETFNT) → $890A가
   그 버퍼에서 글리프를 읽어 VRAM 전송.
 - $8845의 특수분기($8741 코드): 내장 글리프 16바이트를 ($FA),Y로 "직접 복사"함 → 즉 BIOS
   EX_GETFNT는 ($FA/$FB) 버퍼에 글리프를 써 넣는 함수이지, $F8/$F9에 포인터를 돌려주는 함수가
   아님. 부트 렌더러도 $686E에서 $FA/$FB=$2A61로 세팅 후 그 버퍼에서 읽음.
따라서 "copy-to-$FA" 훅이 BIOS 규약과 일치. 진행 내용 9의 "포인터 반환" 전제는 잘못된 것이며,
$21E0 방식으로 되돌리지 말 것. (참고: 훅이 마지막에 $FA를 +32 전진시키지만, 모든 렌더러가 매
글자 $FA를 재설정하고 $890A/$68A1이 고정 주소에서 읽으므로 실무상 무해.)
