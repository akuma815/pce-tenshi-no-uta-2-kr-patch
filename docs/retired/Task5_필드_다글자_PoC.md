# Task 5 — 필드 8글자 다글자 PoC

**정적 PASS / 다글자 표시 PASS / 메모 진입 안정성 FAIL**

> 2026-07-17 안정성 갱신: 첫 필드 이탈과 필드 메뉴 표시는 정상이나 `메모` 선택 즉시
> EmuHawk가 응답 없음 상태가 되었다. 표시 성공은 유지되지만 Task 5 전체 승인은 취소한다.
> 우선 가설은 `$C800~$C8FF` 256바이트 글리프 페이지가 메뉴 전환 데이터와 충돌한다는
> 것이며, 훅과 8개 커스텀 코드를 유지한 채 해당 페이지만 원본 `FF`로 되돌린 격리
> 진단으로 판별한다.

## 표본과 바이트 정책

- 원본 엔트리: `iso:010B9E7`
- 원문: `支度は出来たのかフェイト`
- 현재 번역: `준비는 다 됐나, 페이트`
- PoC 표시문: `준비는다됐나페이`
- 원문 본문 예산: 16바이트
- PoC 본문: 완전한 2바이트 코드 8개, 16바이트

원문은 화면상 12자지만 한자 4개만 2바이트이고 나머지는 1바이트라 실제 저장 예산은
16바이트다. 현재 번역을 마지막 완전 글리프 경계에서 잘라 8글자로 만들었다. ASCII `0x20`,
패딩, 원문 tail, 종료자 변경은 전혀 사용하지 않는다. `준`은 받침, `됐`은 복합모음과 받침을
포함하므로 소형 폰트의 대표 위험도 함께 확인한다.

## local map과 glyph pool

| 코드 | 글리프 | 런타임 주소 |
|---|---|---:|
| `EF58` | 준 | `$C800` |
| `EF59` | 비 | `$C820` |
| `EF5A` | 는 | `$C840` |
| `EF5B` | 다 | `$C860` |
| `EF5C` | 됐 | `$C880` |
| `EF5D` | 나 | `$C8A0` |
| `EF5E` | 페 | `$C8C0` |
| `EF5F` | 이 | `$C8E0` |

`EF58~EF5F`는 Task 2의 필드 파서 generic-pair 범위이며, 18,817개 보호 raw 레코드의
모든 인접 위치에서도 출현 0회다. 8개 글리프는 Galmuri8x8에서 생성한 32바이트 형식으로
MPR6=`84`가 가리키는 `$C800~$C8FF` 한 페이지에 둔다.

훅은 `$C737`에서 trail에서 `0x58`을 빼고 5회 shift해 32바이트 인덱스를 만든다. 범위 밖
코드는 모두 `JMP $E060`으로 원본 BIOS에 전달한다. MPR 변경, stack scratch, 공용 Work RAM,
self-modifying pointer를 사용하지 않는다.

## 런타임 PASS 기준

1. 두 번째 대사에 `준비는다됐나페이` 8글자가 순서대로 서로 다르게 출력된다.
2. 다음 원문 일본어 페이지와 페이지 전환이 정상이다.
3. 필드 이탈·재진입 뒤에도 글리프와 그래픽이 오염되지 않는다.
4. 최소 20회 장면 전환 동안 `EXEC BRK`나 그래픽 손상이 없다.

이 PoC는 첫 필드 이벤트의 8글자 local map만 검증한다. 다른 renderer, 전체 글리프 예산,
문자열 재배치와 완전한 번역문은 승인하지 않는다.

## 런타임 중간 판정

2026-07-17 Task 5 전용 CUE의 새 실행에서 다음을 확인했다.

- 첫 페이지의 일본어와 필드 그래픽이 정상이다.
- 다음 페이지에 `준비는다됐나페이`가 8개의 서로 다른 글리프로 선언한 순서대로 출력됐다.
- 받침이 있는 `준`과 복합모음·받침이 있는 `됐`도 서로 구분되며 셀 안에서 판독 가능하다.
- 첫 페이지에서 두 번째 페이지로 정상 전환됐다.

따라서 **다글자 표시 게이트는 PASS**다. 다만 Task 5 전체 PASS 기준에 포함된 필드 이탈·재진입과
최소 20회 장면 전환, 그동안의 `EXEC BRK` 부재는 아직 관측되지 않았다. 전체 상태는
`DISPLAY PASS / STABILITY PENDING`이며, 증거는
`translation/task5_field_multiglyph_poc_runtime.json`이 소유한다.
