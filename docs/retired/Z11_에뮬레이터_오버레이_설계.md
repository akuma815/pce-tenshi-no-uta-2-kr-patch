상태: **Z11.2 성공 (2026-08-30) — 초상화 대사를 원본보다 긴 한글로 출력. 길이 캡 소멸 실증. §4f**
작성: 2026-08-30
결정자: 사용자 (2026-08-30)

## 0. 한 줄 요약

디스크를 수정하지 않고, BizHawk Lua 훅으로 렌더 중인 원문을 가로채
**원본 텍스트 창을 덮어 그린 뒤 그 위에 한글을 출력**한다.
Switch판 천사의 시가 쓴 방식의 실기-외 등가물이다.

## 1. 결정 사항

| 항목 | 결정 |
| --- | --- |
| 적용 범위 | **전면 오버레이** — 모든 텍스트를 Lua가 그린다 |

### 1.1 왜 바꾸는가

b10 v13은 잔존 일문 0·게이트 PASS로 in-place 방식이 갈 수 있는 끝까지 갔다.
남은 블로커 4개가 **전부 같은 병(슬롯 길이 하드캡)**이고, 카드 서브·포인터
재배치가 3중 실측으로 무효 확정(HANDOFF §6)이라 in-place로는 해소 경로가 없다.

| 블로커 | in-place | 오버레이 |
| --- | --- | --- |
| 초상화 대사 83종 (부족 441B) | 축약만 가능 | **캡 소멸** |
| 선택지 예/아니오 (옵션당 2B 고정) | '아니오' 불가 | **캡 소멸** |
| NOFIT 139행 | 창 공간 추가 필요 | **캡 소멸** |
| 후반 몬스터명 205개 (+4,204B) | 도너+축약 병용 | **캡 소멸** |

### 1.2 소멸하는 제약

오버레이로 옮기면 다음이 **설계에서 사라진다**:

- 슬롯 길이 캡 전부, 창 아레나 subset-sum 배치, 축약 작업 83종
- **폰트 문제 전체** — 12×12 BIOS 폰트, 3,417 슬롯 예산,
  `EX_GETFNT` 공식, 수정 시스템카드, 반각/전각 렌더 버그
- 엔진 코드 공간 (`$C737..$C900` 457B 단일 FF run)
- 뱅크 소유권 `$68-$87`, MPR 규율, VRAM, 트램펄린, armchk, 카드 상주
- HANDOFF §3 절대 규칙 1~8 중 텍스트 층에 적용되는 항목 대부분

### 1.3 받아들이는 비용

- **BizHawk 종속.** Mednafen·Ootake·RetroArch·실기 전부 불가.
  배포물이 `.cue/.bin` 패치가 아니라 **원본 디스크 + Lua + 데이터 파일**이 된다.
- **스크립트 없이는 순수 일본어 게임.** 우아한 성능 저하가 아니라 미적용이다.
- b10 v13 빌드는 배포물에서 빠진다. **번역 텍스트는 100% 재사용**되고,
  빌드 자체는 대조·회귀용 참조로 보존한다.

## 2. 아키텍처

```
  event.on_bus_exec @ $F124 (EX_GETFNT entry)
        │  zp $F8/$F9 = 렌더 중인 SJIS 1문자, $FF = font mode
        ▼
  문자 누적 → 레코드 경계 판정 → 원문 문자열 재구성
        │
        ▼
  조회: 원문 문자열 (또는 source key) ──▶ overlay_subtitles.csv
        │
        ▼
  gui: 해당 텍스트 창 rect 를 불투명 박스로 덮고
       그 위에 한글 그리기
```

핵심은 **개입점을 데이터 층에서 렌더 층으로 옮긴 것**이다.
지금까지는 "어떤 바이트를 먹일까"로 싸웠고 초상화 클래스가 어느 훅도 안 타서
막혔다. 렌더 층은 **커버리지 100%가 이미 실측**돼 있다.

## 3. 확정 근거 (재조사 금지)

### 3.1 단일 렌더 초크포인트

HANDOFF §6 / Z6:

> 모든 텍스트는 상주 `field.main_engine`의 `$967E`(MPR4=`$82`) GETFNT를 통과한다.
> **1,602회 trace 전수 확인.** 전투·Memo·탑·**초상화** 전용 renderer는 존재하지 않는다.

초상화 클래스가 `$4284` 디스패처를 안 타는 것(b11/b12 3중 실측)은
**스트림 층**의 사실이고, 렌더 층에는 해당하지 않는다.

### 3.2 렌더 훅 ABI — **2026-08-30 실측 정정**

| 지점 | 주소 | 실측 |
| --- | --- | --- |
| 게임 렌더러 | **`$967E`** (MPR4=`$82`) | 36회 발화 |
| BIOS EX_GETFNT entry | `$F124` | 35회 발화 |
| BIOS source copy | ~~`$F1B9`~~ | **0회 — 발화하지 않음** |

- **문자 코드 = zp `$F8`/`$F9` 의 리틀엔디언 u16 SJIS.**
  `sjis = zp($F8) + zp($F9) * 256` (즉 `$F9`=lead, `$F8`=trail).
  ⚠ `trace_ex_getfnt_source.lua` 주석의 "`$F8`=lead, `$F9`=trail" 은 **뒤집혀
  있었다.** 실측 디코드로 정정: `8E9E`=時 `8AD4`=間 `95AA`=分
  `8DC5/8F89/82A9/82E7`=最初から `82CC`=の `8140`=전각공백 `815B`=ー —
  전부 같은 프레임의 화면(로드 메뉴)과 일치.
- **`$F1B9` 는 발화하지 않는다.** `translation/ex_getfnt_source_trace.tsv` 가
  비어 있던 진짜 원인이 이것이다(텍스트 부족이 아님). 이 주소는 쓰지 말 것.
- **`$967E` : `$F124` = 1.03** — 게임 렌더러와 BIOS 폴백이 사실상 1:1.
  초과분 1건은 텍스트 이전 프레임(f534, `mode=$82`)의 초기화성 호출.
- zp 접근 = `memory.read_u8(0x2000 + addr, "System Bus")`.
- 코어는 **PCEHawk 필수** (`event.on_bus_exec` 가 PCEHawk 에서만 발화).
  카드 = `probes/SystemCard3_original_noheader.pce`, 설정 =
  `cfg_pcehawk_diag.ini` 사본이 **이미 Z11 목표 구성과 일치**(원본 디스크·원본 카드).

### 3.2a gui 렌더 ABI (P3 실측)

- **`gui.use_surface("emucore")` 필수.** 이걸 안 하면 그린 내용이
  `client.screenshot` 에 안 잡힌다(클라이언트 레이어로 감). 좌표는 **게임
  네이티브 픽셀 공간**이고 렌더는 **디스플레이 해상도**로 나가 선명하다.
- 동작 확인: `gui.drawText`(기본 폰트 / `Malgun Gothic`), `gui.drawString`(`Gulim`),
  `gui.drawRectangle`(불투명 박스). **`gui.text` 는 emucore 표면에 안 나온다 — 쓰지 말 것.**
- `client.screenshotClient` 없음. OSD 포함 토글 = `client.setscreenshotosd`.
- 종료는 **`client.exit`** (`client.exitprogram` 은 이 빌드에 없음).

### 4a.1 P2 판정 근거 (2026-08-30)

**초상화 대사는 렌더 층에서 다른 텍스트와 구별되지 않는다.**
in-place 트랙이 3중 실측으로 "어떤 훅도 안 탄다"고 확정한 것은 **스트림 층**
(`$4284`/armchk) 사실이며, 렌더 층에는 적용되지 않는다 — 설계 전제가 실증됐다.

증거: `translation/z11_probe/harvest/` (실플레이 수확 361 이벤트 / 6,471자).
화자명 `：` 패턴으로 초상화 대사 12건 포착, 그중 [40]·[361] 의 원문이
초상화 창 스크린샷과 픽셀 단위로 대응.

### 4a.2 세이브스테이트 프로브의 함정 (재시도 금지)

`diag_portrait_pcehawk.State` 로 P2 를 직접 재현하려 한 2회 시도는 **무효**다
(FAIL 아님). 이유 두 가지:

1. **정지 화면은 렌더 호출이 0이다.** 상태 저장 시점에 대사는 이미 VRAM 에
   타일로 그려져 있다. 새 문자가 그려지지 않으면 훅이 안 걸리는 게 정상이다.
2. **상태 로드 이후 `joypad.set` 입력이 먹지 않는다.** 900 프레임 동안 화면
   변경 픽셀이 22개뿐이었고, 그것도 (160,202) 의 입력 대기 커서 깜빡임이었다.
   훅 등록을 상태 로드 **이후**로 옮겨도 동일. (부팅에서는 같은 펄스 패턴이
   정상 동작 — HANDOFF §9 의 자동 내비게이션 함정과 같은 계열)

→ **렌더 훅 검증은 세이브스테이트가 아니라 실플레이 수확으로 한다.**
   `run_z11_harvest.cmd` 가 그 목적의 도구다.

### 4a.3 수확 도구의 알려진 결함 — **수정 완료, 단 절반만 해결 (2026-09-01)**

`harvest_z11_windows.lua` 는 QUIET(12프레임) 뒤에 zp 를 샘플링하므로
**스트림 포인터가 이미 정리된 값**이었다(`zp52/53=43/00` 또는 `00/00`).
→ **버스트 첫 문자 시점에 샘플링**하도록 고쳤고, `frame0` 열(버스트 시작 프레임)을
추가했다. 기존 361행은 `frame0=0` = "구 결함 샘플, 포인터 키로 쓰지 말 것".

**실측(일회용 프로브, `diag_portrait_pcehawk.State`, 버스트 4건):**

| 버스트 | 시작 시점 zp52/53 | QUIET 후 zp52/53 |
| --- | --- | --- |
| 1 (25자, 초상화) | `43/00` | `43/00` |
| **2 (14자, 메모)** | **`A6/DE`** | `43/C0` |
| 3 (32자, 초상화) | `43/00` | `43/00` |
| 4 (25자, 초상화) | `43/00` | `43/00` |

→ **살아 있는 포인터가 있으면 시작 샘플이 그것을 잡는다**(메모 창: `A6/DE` 대 정리값
`43/C0`). 그러나 **초상화 클래스는 렌더 시점에 애초에 스트림 포인터가 없다**
(`$53=00` → 디스패처 우선순위상 `$52/$53` 경로가 아님). 이는 샘플링 결함이 아니라
HANDOFF §6 클래스 지도의 사실(초상화 = 별도 페치 루프)이 렌더 층에서 확인된 것이다.

> **결론: 스트림 포인터는 전 클래스 공통 키가 될 수 없다.** §5.2a 의 포인터 식별
> 경로는 메모·일반 대사에만 유효하다. 레코드 식별의 주 경로는 계속 **원문 문자열
> 매칭**(§5.1)이며, 지금 그것으로 수확 범위 100% 가 나온다.

### 4b.1 확정된 BAT ABI

- **BAT base = `$0000`(VRAM1 바이트), 행 stride = `$80`, 64칼럼 × 2바이트.**
- BAT 엔트리(리틀엔디언 u16) = `타일 = e % 4096`, `팔레트 = e / 4096`.
- 셀 → 픽셀: `x = col*8`, `y = row*8`.
- **12px 글자는 8px BAT 행 2개에 걸친다** → 인접 행을 **최대 2행까지만** 병합해야
  텍스트 줄이 된다. 무제한 체이닝하면 화면 전체가 한 덩어리로 뭉친다(실측 버그).
- 줄 안의 칼럼 런 = 세그먼트. 문자수 검산 일치
  (`２．最初から` 6자 × 12px = 72px = 9셀, 실측 9셀).
- 검출 방법 = **버스트 전/후 BAT diff**. 스캔 범위 `$0000..$1000`(32행) 이면 충분.
- 예측 영역은 실제 글자의 **상위집합**이라 덮기에 안전 (예측 x=32..335 / 실측 32..322).

### 4b.2 창 배경색 산출 (팔레트 직접 계산)

글자 런 옆 셀의 BAT 엔트리 → 타일 → 픽셀 색인 → `VCEPalette`.
PCE 팔레트는 9비트 GRB(`G=bits6-8, R=bits3-5, B=bits0-2`), 엔트리는
`(팔레트번호*16 + 색인)*2` 바이트. 하드코딩 불필요.
※ 로드 화면은 창이 없는 검은 배경이라 `idx=0`(백드롭) 이 정상이다.

### 4b.3 렌더 규칙 (둘 다 필수 — 어기면 눈에 보이는 결함)

1. **2패스 렌더**: 모든 세그먼트를 먼저 덮고, 그다음 모든 한글을 그린다.
   세그먼트마다 덮기→글자를 반복하면 **뒤 세그먼트의 덮기가 앞 세그먼트의
   한글을 잘라먹는다**(실측).
2. **덮기 영역에 6px 패딩**. 글자가 셀 경계를 넘어 삐져나와 잔여 픽셀이 남는다.
   한글은 패딩 없이 원래 글자 자리(`col*8`, `row*8 - 1`)에 그린다.

### 4b.4 BizHawk 함정

- **`client.setscreenshotosd(true)` 가 없으면 오버레이가 스크린샷에 안 잡힌다.**
  gui 호출은 전부 OK 를 반환하는데 결과가 안 보여 오진하기 쉽다.
  판별법 = 스크린샷 해상도. 오버레이가 합성되면 `704×468`(2배), 아니면 `352×234`.
- `gui.use_surface("emucore")` 는 **조기 반환보다 먼저** 호출해야 한다.

### 4b.5 남은 과제

- 버스트가 **여러 창을 하나로 묶는다** (예: 대사 + 선택지 `はい/いいえ` 가 한 버스트).
  세그먼트 단위로는 분리되므로 번역을 세그먼트에 맞춰 쓰면 된다.
- 스크롤하는 필드 화면에서 BAT 좌표가 그대로 맞는지 미검증 (로드 화면은 무스크롤).
- PoC 번역문 4건은 **작업용 초벌**이다. 실제로는
  `script_sheet.tsv`·`btrack_b3_translation_map.tsv` 의 검수된 번역을 쓴다.

## 4c. Z11.2 결과 — 파이프라인은 통과, **위치 매핑 실패** (2026-08-30)

도구 `tools/overlay_z11_2.lua`, 증거 `translation/z11_probe/z11_2.log` /
`z11_2_01.png`. 상태 = `diag_portrait_pcehawk.State`(초상화 대사).

### 통과한 것

- 훅 발화 → 버스트 분절 → **초상화 대사 32자 키 매칭 성공**(`match=YES`)
- **창 배경색 산출 정확**: `pal=15 GRB=3,0,0` → `#006D00`
  = 스크린샷 분석으로 얻었던 대사창 색과 완전 일치. **팔레트 경로 실증 완료.**
- 세그먼트 6개 검출(번역 3개와 개수 불일치는 아래 위치 문제의 부산물)

### 실패한 것 — 스크롤 화면에서 BAT→화면 좌표가 어긋난다

검출 좌표가 `px=(384,0)`(화면 폭 352 초과), 행이 `29..31` 과 `0..3` 으로 갈라짐.
64칼럼·32행 BAT 의 **랩어라운드**다. 실제 화면에서 한글은 **좌상단**에 그려졌고
하단 초상화 대사창은 원문 그대로 남았다.

- **Z11.1(로드 화면)이 통과한 이유 = 그 화면은 스크롤이 없어서** 셀→픽셀이
  우연히 직접 대응했다. §4b.1 의 `x=col*8, y=row*8` 은 **무스크롤 화면 한정**이다.
- 필드는 배경이 스크롤하므로 화면 원점이 BAT 원점과 다르다.
  `screen_col = (bat_col - BXR/8) mod 64`, 행도 동일하게 `BYR` 보정이 필요하다.

### 다음에 할 일 — 스크롤 레지스터 확보

`emu.getregisters()` 는 **CPU 레지스터만** 노출한다(A/X/Y/S/PC/플래그/MPR).
VDC 레지스터(BXR=#7, BYR=#8)가 없으므로 다음 중 하나로 얻어야 한다.

1. **VDC 포트 쓰기 훅** — `event.on_bus_write` 로 `$0000..$0003` 감시,
   레지스터 선택값을 추적해 BXR/BYR 을 그림자 변수로 유지. (가장 직접적)
2. **RAM 그림자 탐색** — 게임이 스크롤 값을 RAM 에 두고 VDC 에 복사할 가능성.
   제로페이지 전수 덤프(v4 방식)를 스크롤 이동 중에 떠서 상관 분석.
3. **창 앵커 매칭** — 창 배경 타일이 깔린 BAT 영역을 찾아 그 자체를 원점으로
   삼는다. 스크롤과 무관해지지만 창 타일 식별이 선행돼야 한다.

**권장 = 1번.** 훅 비용이 이미 0에 가깝고(239fps), 정확하며 게임 무관이다.

## 4d. 인게임 창 위치 매핑 — 방법 3종 실패 기록 (2026-08-30)

**재시도 금지.** 아래 셋은 전부 실측으로 배제됐다. 파이프라인의 나머지
(훅·SJIS 판독·버스트 분절·키 매칭·창색 산출·렌더)는 전부 통과 상태다.

| # | 방법 | 결과 | 원인 |
| --- | --- | --- | --- |
| 1 | **BAT diff** (버스트 전/후 비교) | ❌ | 스크롤·애니메이션 화면에서 배경 갱신이 diff 를 뒤덮는다. 초상화 버스트에서 `행0..31 칼럼0..63` = BAT 전체가 변경으로 잡힘 |
| 2 | **글자 직후 BAT 쓰기 상관** (MAWR 추적) | ❌ | **게임은 글자마다 BAT 를 쓰지 않는다.** 277글자 렌더에 BAT 셀 포착 1건. 창이 열릴 때 BAT 가 고정 타일 슬롯을 가리키도록 세팅되고, 글자 렌더는 **그 타일의 패턴만 덮어쓴다** |
| 3 | **타일번호 역추적** (쓰인 타일 → BAT 스캔) | ❌ | 같은 구간에 배경 애니메이션·초상화 이미지 업로드가 섞인다. 32글자 버스트에 **타일 611개·셀 183개**가 잡혀 분리 불가 |
| 4 | **창 영역 한정 BAT diff** | ❌ | 창 영역(행17..26 칼럼2..42) 안에서 **변경 셀 0개**. → 게임은 창의 BAT 를 아예 건드리지 않는다(중요 확증) |
| 5 | **창 영역 한정 + 타일 매칭** (3+4 합성) | ❌ | 결과가 비일관. 정작 초상화 버스트는 **타일 611개에 셀 0개**, 다른 버스트는 창 영역 **전체 509셀**이 매칭 |

### 함께 확인된 사실

- **VDC 스크롤 레지스터는 쓰기가 관측되지 않는다.** `$0000` 로 선택되는 레지스터는
  R0(MAWR)·R1(MARR)·R2(VWR) 뿐 (900프레임, R2 1792회). BXR(#7)/BYR(#8) 0회.
  → 다만 이는 **"스크롤이 0"이라는 뜻이 아니다.** 세이브스테이트 이전에 설정되고
  이후 갱신되지 않았을 가능성이 크며, **BXR/BYR 은 PCE 에서 쓰기 전용이라 읽을 수 없다**
  (`emu.getregisters()` 는 CPU 레지스터만, VDC 도메인 없음).
- **`$0402/$0403` 는 VDC 미러가 아니라 VCE(팔레트) 포트다** — 초기 가정 오류, 정정됨.
- 검출 좌표가 반복적으로 `칼럼46..63 + 0..10`(랩어라운드)·`x=368/480`(화면 352 초과)
  로 나온다 → 화면 원점이 BAT 원점과 다르다는 일관된 신호.

### 스프라이트 가설 — **기각 (2026-08-30 실측)**

`tools/probe_z11_satb.lua` 로 VRAM 전역에서 SATB 후보를 점수화했다.
**유효 후보 0개.** 최고점 위치들의 데이터는 화면좌표 `(736,704)`,
속성 `$FF00` 등 명백한 쓰레기값이다. 텍스트가 스프라이트라면 대사창 y대역에
x 가 12~16px 간격으로 늘어선 엔트리 뭉치가 보여야 하는데 없다.
→ **텍스트는 BG 다.** 아래 항목은 기록만 보존한다.

### **더 근본적인 문제 — BAT 모델이 인게임 화면을 설명하지 못한다 (2026-08-30)**

`tools/probe_z11_batdump.lua` 로 대사 표시 중 BAT 전체를 타일번호로 덤프했다.

- 대사창이 화면 y=144~200(행 18~25)에 있다면 그 행들에 **단일 타일이 40셀가량
  길게 깔린 구간**이 나와야 한다. 실제로는 **행 18~25 가 행 4~17 과 구별되지 않는다**
  — 전부 `타일$242 x12~18 @칼럼34, pal=4` 로 동일.
- 화면에는 방·초상화·대사창이 있는데 덤프는 단조로운 반복만 보인다.

→ **`BAT base=0 · 64칼럼 · x=c*8,y=r*8` 모델은 인게임 화면에 성립하지 않는다.**
Z11.1(로드 화면)이 통과한 것은 그 화면에 한해 우연히 맞았을 가능성이 크다.
방법 1~5 가 전부 실패한 공통 원인이 여기에 있을 수 있다.

### 다음 — 가설 말고 **지상검증(ground truth)** 으로 간다

여섯 번째 가설을 세우지 말 것. 대신 **화면을 재구성해 정답 기하를 역산**한다.

1. 대사 표시 중 `VRAM1` 전체 + `VCEPalette` 전체를 파일로 덤프하고
   같은 순간의 스크린샷을 남긴다.
2. 파이썬에서 BAT 기하 후보(64x32 / 128x32 / 32x64 / 64x64)와 BAT base 후보를
   바꿔가며 화면을 렌더링해 **스크린샷과 픽셀 비교**한다.
3. 재현되는 조합이 곧 정답이다. 그때 비로소 셀→화면 변환식이 확정된다.

이 방법은 추측이 아니며 한 번에 끝난다. **이것이 나오기 전에는 위치 매핑을
더 구현하지 말 것.**

### (기록 보존) 스프라이트 가설의 근거였던 관측

방법 4·5 의 결과가 이 가설로 일관되게 설명된다.

- 창 영역 BAT 가 **전혀 변하지 않는다**(방법 4, 변경 0셀)
- 창의 BAT 셀이 **쓰인 타일을 가리키지도 않는다**(방법 5, 초상화 버스트 0셀)
- 그런데 글자 렌더 중 VRAM 에 패턴은 대량으로 쓰인다(타일 611개)
  → **스프라이트 패턴**도 VRAM 에 있으므로 모순이 없다

사실이라면 글자 위치는 BAT 가 아니라 **SATB(스프라이트 속성 테이블)**에 있다.
SATB 는 VDC 레지스터 #13(DVSSR)이 가리키는 VRAM 주소이며, 이 게임은
R0/R1/R2 외 레지스터를 쓰지 않으므로 **DVSSR 도 세이브 이전에 설정**돼
관측 불가일 가능성이 크다.

**확인 방법(저비용)**: VRAM 상위 영역에서 SATB 후보를 찾아 스프라이트
엔트리(y, x, 패턴, 속성 4워드 × 64)를 덤프하고, 대사창 y 좌표(≈144~200)와
맞는 엔트리가 64개 중 몇 개인지 센다. 맞으면 스프라이트 확정.

### 이전에 세웠던 다음 진단 (①은 완료)

① 자유 이동 중 BXR/BYR 관측 = **완료**. 이동 중에도 R0/R1/R2 만 선택되고
BXR/BYR/MWR 은 0회 → 스크롤 레지스터 방식이 아님이 확정. BAT→화면은
직접 대응이 맞다(Z11.1 이 통과한 이유).

### 다음 진단 (착수 전 이것부터)

위치 문제의 정체를 **먼저 확정**하고 방법을 고를 것. 추측으로 구현하지 말 것.

1. **자유 이동 중 BXR/BYR 쓰기 관측** — 대사 중이 아니라 **걸어다니는 동안**
   `$0000` 의 R7/R8 선택을 감시한다. 관측되면 스크롤 방식이 확정되고 보정식이 나온다.
   관측되지 않으면 게임이 BAT 재작성으로 스크롤한다는 뜻이다.
2. **BAT 기하 확인** — 화면 352px = 44셀인데 검출이 64칼럼을 넘나든다.
   MWR(가상화면 크기)이 64×32 가 맞는지, 창이 BAT 어느 영역에 놓이는지 확인.
3. **대안 앵커** — 위 둘로도 안 풀리면, 창 배경 타일이 깔린 BAT 영역을 찾아
   **창 자체를 원점으로** 삼는다(§5.2b 3번안). 스크롤과 무관해진다.

## 4e. 지상검증 — **정답 기하 확정 (2026-08-30)**

도구 `tools/probe_z11_dump.lua`(원자재 덤프) + `tools/gt_reconstruct.py`(재현·역산).
증거 `translation/z11_probe/gt/` (`vram.bin`·`palette.bin`·`screen.png`·`recon_best.png`).

방법 = 대사 표시 중 VRAM 64KB + 팔레트 1KB + 스크린샷을 같은 시점에 덤프하고,
파이썬에서 BG 를 렌더링해 **스크린샷과 픽셀 비교**로 기하를 역산.

### 확정값 — 일치율 **93.6%**

| 항목 | 값 |
| --- | --- |
| BAT 크기 | **64 × 32** |
| BAT base | **$0000** (VRAM 워드) |
| 색 비트순서 | **GRB** — `G=bit6-8, R=bit3-5, B=bit0-2`, 각 3bit → `v*255/7` |
| 화면 원점 | **BAT 픽셀 (352, 82)** = BXR 352 / BYR 82 |

**셀 → 화면 변환식**

```
screen_x = (col * 8 - 352) mod 512
screen_y = (row * 8 -  82) mod 256
```

나머지 6.4% 는 캐릭터 스프라이트다(초상화·대사창·방은 전부 BG 로 재현됨).

### 이전 결론 2건 정정

1. **"BAT 모델이 인게임 화면을 설명 못 한다" → 틀렸다.**
   `base=0, 64×32` 는 **처음부터 옳았다.** 틀린 것은 화면 원점을 (0,0) 으로

4. 이 원점으로 검출된 글자 셀을 §4e 변환식에 넣으면 화면 좌표가 나온다.

정적 값은 **화면 좌표 하나뿐**이고 그것은 이미 자동 추출된다.

## 4h. 자리표시자 패턴 매칭 (2026-08-30)

### 문제

코퍼스 레코드 5,972종이 `{%s}`/`{%d}` 자리표시자를 갖는다.
`clean()` 이 이 토큰을 **제거**하면 원문이 이어붙어 매칭 불가능한 문자열이 된다:

```
원본  {%s}は{%s}の呪文を唱えた！
제거후 れはの呪文を唱えた！          ← 매칭 불가
한글  %s(은)는 %s의 주문을 외웠다！
```

### 해법

제거가 아니라 **와일드카드로 치환해 패턴 등록**한다(`make_pattern`).
`{%d}` → `([0-9０-９]+)`, `{%s}` → `(.{1,12}?)`. 캡처값은 `pairs` 로 번역을 시도하고
(이름류가 Z8 색인에 있으므로 대개 성공), 한글 템플릿의 `%s`/`%d` 에 순서대로 채운다.
정확 매칭 실패 시에만 시도하며, 각 패턴의 **가장 긴 리터럴 조각**으로 선필터한다
(패턴 7,956종을 매 위치에서 다 돌리면 느리다).

### 결과

| 지표 | 이전 | 이후 |
| --- | ---: | ---: |
| 완전 매칭 버스트 | 55 | **69** |
| 부분 매칭 | 70 | 56 |
| **세그먼트 커버리지** | 76.0% | **79.9%** |

### 진단 과정에서의 오진 2건 (기록)

1. 깨진 출력을 보고 **패턴 매칭 탓으로 오진**해 품질 게이트를 걸었으나
   **수치가 전혀 변하지 않았다**. 실제 원인은 정확 매칭 쪽이었다.
2. 진짜 원인 = **Z8 색인에 섞인 1글자 항목**(`あ`→`아` 류)이 탐욕 분할기에서
   텍스트를 잘게 부순 것. **1글자 항목 색인 제외**로 품질 의심 9건 → 5건.
3. `페이트||레벨||HP` 의 빈 칸을 손상으로 봤으나 **오해**였다 —
   그것은 미매칭 일본어 자리이며, §4g 안전장치대로 덮이지 않아 원문이 보인다.
   설계된 동작이다.

| 1 | **`_hint` 가 정규식 문자열에서 앵커를 역추적** | `[0-9０-９]` 의 **문자클래스 내부**가 앵커로 잡혀(`0-9０-９`) 본문에 없는 문자열이 된다 → `{%d}` 를 가진 패턴이 **전량 선필터에서 배제**. `{%s}は{%d}のダメージ！` 는 코퍼스에 있는데 후보에조차 오르지 않았다 | 앵커를 `make_pattern` 에서 **직접 기록**(리터럴 조각 그대로) |
| 2 | **한글 템플릿의 `{%s}` 를 `clean()` 이 제거** | Z8 색인 4,210행 **전부** 한글 쪽이 `{%s}` 형태다. 채울 자리가 사라져 `{%s}는{%d}피해!` → `는피해!` 가 되고, "원문 대비 과도하게 짧음" 게이트에 걸려 폐기 | 지우기 전에 `%s`/`%d` 로 치환 |
| 3 | **탐욕 분할이 정확 매칭을 무조건 먼저 채택** | `クロウラーは８のダメージ！` 에서 이름 `クロウラー` 만 집어먹고 남은 `は８のダメージ！` 를 버린다. 미번역 30종 중 20종이 이 형태 | 같은 위치에서 **패턴이 더 길면 패턴을 택한다** |
| 4 | **`fill()` 이 줄마다 캡처 인덱스를 0으로 리셋** | 여러 줄 템플릿이 첫 캡처만 반복 — `６の経験値と３ギミル` → `６경험치와\|**６**기밀을얻었다` | `vi` 를 줄 넘어 유지 |

### 3번의 부작용과 안전장치 — `caps_ok`

"패턴이 길면 이긴다"만 넣으면 `{%s}` 의 `.{1,12}?` 가 **앞 문맥을 통째로 삼킨다**.
실측: `フェイトシオン　シオンは１のダメージ！` → `フェイトシオン　シオン는１피해!`
— 캡처에 채울 번역이 없어 **일본어가 그대로 출력**됐다. 정확 매칭보다 나쁘다.

> **규칙**: 패턴이 이기려면 **모든 캡처가 번역 가능**해야 한다.
> 번역 가능 = 코퍼스에 있거나, 애초에 번역이 필요 없는 숫자·기호·공백.
> 아니면 그 패턴은 후보에서 탈락하고 정확 매칭으로 되돌아간다.

같은 이유로 능력치 라벨은 `{%s}が{%d}あがった` 로 두지 않고 **라벨마다 한 줄씩**
적는다(`ＡＰが{%d}あがった` …). 라벨은 코퍼스에 낱개로 없어 캡처가 번역되지 않는다.

### 공백 런은 커버리지 분모에서 뺀다

미번역 113개 중 **60개가 전각 공백 한 칸**(파티창 여백 `フェイトシオン　`)이었다.
번역할 것이 없으므로 덮지도, 세지도 않는다. 이걸 빼야 지표가 정직해진다.

### 새 입력 파일 — `translation/z11_overlay_supplement.tsv`

엔진이 라벨·이름·수치를 **런타임에 이어붙이는** 문장은 디스크 텍스트 레코드가
아니라서 어느 코퍼스에도 원문 그대로 없다. 손으로 쓴 17행을 여기에 둔다
(회심의 일격·방어 태세·레벨업·능력치 상승·로드 화면 슬롯·메모 항목·`バルーン`).

- 형식 `jp <TAB> ko <TAB> note`, `#` 주석 허용, `{%s}`/`{%d}` 사용.
- **가장 먼저** 읽어 `setdefault` 우선권을 준다.
- 이 파일의 패턴은 **신뢰 패턴** — 자동 생성 패턴에 걸리는 "리터럴 앵커 4자 이상"
  게이트를 면제받는다(로드 화면 `Ｌ{%d}{%s}{%d}時間{%d}分` 은 앵커가 `時間` 2자뿐).
- `b10_unindexed_battle.tsv` 에도 비슷한 문장이 있으나 그쪽은 **in-place 슬롯 길이에
  맞춘 축약본**(`치명타!`, `방어중`)이다. 오버레이는 길이 제약이 없으므로 원복한다.

### 조사 자동 보정 — 오버레이에서만 가능한 것

코퍼스 템플릿은 `{%s}는{%d}피해!` 처럼 조사가 **한 쪽으로 고정**돼 있어
`고블린는` / `벌룬는` 이 나온다. in-place 는 엔진이 런타임에 이름을 넣으므로
조사를 고를 수 없어 **아예 빼는 것**이 규칙이었다(HANDOFF §6).
오버레이 생성기는 **생성 시점에 실제 이름을 안다.** 그래서 채워 넣은 값의 받침을
보고 은/는·이/가·을/를·과/와·(으)로를 고른다(`fix_josa`). 숫자는 마지막 자리의
한국어 읽음으로 판정한다(2=이 받침없음, 8=팔 받침있음 …).

→ `고블린은７피해!` · `고블린이나타났다!` · `벌룬이쓰러짐!` (실측 출력)

안전성 확인: 전 코퍼스에서 `{%s}` 바로 뒤에 조사 후보 글자가 오는 경우는
**38건뿐이고 전부 진짜 조사**다(`{%s}이야기` 같은 오검출 대상 0건).

**괄호 병기는 쓰지 않는다 (2026-09-01 사용자 결정).** `(은)는` 은 채워질 이름을
*모를 때* 쓰는 표기인데 오버레이는 안다. 코퍼스에 두 방식이 섞여 있어서
— `ziria_z8_text_entry_index.csv` 18,817행에는 괄호가 **0건**(한쪽 고정),
`script_sheet.tsv` 에만 **31행**이 `%s(은)는 …` 꼴 — `fix_josa` 가 괄호형도
인식해 **한쪽으로 접는다**. 안 접으면 화면에 `클로우(은)는` 이 그대로 나간다.

| 템플릿 | 채운 값 | 출력 |
| --- | --- | --- |
| `%s(은)는 %s의 주문을 외웠다！` | シオン / ライヒ草 | `시온은 라히초의 주문을 외웠다！` |
| `%s(이)가 완쾌되었다！` | フェイト / シオン | `페이트가` / `시온이 완쾌되었다！` |
| `%s(을)를 사용했다` | ライヒ草 | `라히초를 사용했다` |
| `%s(으)로 갔다` | アーウィンの街 | `아윈마을로 갔다` (ㄹ 받침) |

생성 결과 내 괄호 조사 **0건** 확인.

### 진단 산출물 — `overlay_unmatched.tsv`

생성기가 미번역 세그먼트를 `count / jp_segment / burst_sample` 로 적어 낸다.
릴리스 판정 지표(세그먼트 커버리지)와 그 구멍의 정체를 한 파일에서 본다.

### 매처 자기검증 (§4f 잔여 결함 1 해소)

`find_origin` → **`find_candidates`**: 크기 조건에 맞는 클래스를 하나로 좁히지 않고
점수 내림차순 **후보 목록**(최대 12)으로 돌려준다. 호출부가 후보마다 `detect` 를
돌려 **창 안 텍스트 셀이 가장 많은 것**을 채택한다. 틀린 클래스는 셀이 거의 안
잡힌다. 동점이면 블록 점수가 높은 쪽을 유지한다.

실측: 버스트 1 은 후보 2개였고 자기검증이 78셀 쪽을 골랐다 —
원점 `(352,82)` 로 §4e 지상검증 정답과 일치. 기존 정답을 깨지 않는다.

## 4j. Z11.3 준비 — 수확 반복이 가능한 파이프라인 (2026-09-01)

Z11.3 은 **사용자 플레이가 있어야 진행되는 단계**다. 그 전에, 수확을 되풀이해도
앞 판이 망가지지 않고 표가 자동으로 따라오도록 파이프라인을 고쳤다.

### 고친 것 3가지

1. **수확이 이어붙는다** (`harvest_z11_windows.lua`).
   전에는 `harvest.tsv` 를 `"w"` 로 열어 **매 실행마다 덮어썼고**, `shot` 도 1부터
   다시 세어 스크린샷 파일명이 겹쳤다. 두 번째 판을 돌리는 순간 현재 커버리지의
   근거(361 이벤트)가 사라진다. → 기존 마지막 `shot` 을 읽어 그 다음부터 이어 쓰고,
   헤더는 파일이 비었을 때만 쓴다.
   **실측 확인**: 스모크 실행 후 헤더 1줄 유지, 기존 361행 md5 불변,
   로그에 `수확기 가동 (기존 361건에 이어 씀)`.
2. **클래스 표 생성이 도구가 됐다** (`tools/build_overlay_classes.py`).
   47종 표는 원래 손으로 뽑아 오버레이에 붙여 넣은 것이었다. 규칙을 복원해
   도구로 만들었다 — `overlay_rects_detected.tsv` 에서 `#000000` 을 빼고
   `(색, x, y, w, h)` 로 묶어 **hits ≥ 3** 만 채택(창 후보 1,057 → 그룹 79 → 47).
   기존 인라인 표와 **완전 일치**함을 확인했다.
3. **오버레이가 표를 복사해 두지 않는다.**
   `overlay_z11_final.lua` 의 인라인 47행을 지우고
   `dofile(OUTDIR .. "/classes.lua")` 로 바꿨다. 수확을 넓히면 표가 바뀌는데,
   손으로 옮겨 적으면 실측과 어긋난다. **어긋난 클래스는 원점을 통째로 틀리게 하고,
   매처 자기검증도 못 구한다 — 후보 목록에 정답이 없으면 걸러 낼 것이 없다.**
   **실측 확인**: 리팩터 후 재실행 로그가 직전 실행과 완전히 동일.

### Z11.3 실행 순서 (사용자 플레이 필요)

```
1) run_z11_harvest.cmd                       # 중·후반 구간을 골고루 지나갈 것
2) python -X utf8 tools/build_overlay_rects.py translation/z11_probe/harvest/*.png
3) python -X utf8 tools/build_overlay_classes.py
4) python -X utf8 tools/build_overlay_subtitles.py
   -> 세그먼트 커버리지 + translation/z11_probe/overlay_unmatched.tsv 로 판정
5) 미번역 세그먼트를 translation/z11_overlay_supplement.tsv 로 보충하고 4) 반복
6) 오버레이 실행으로 런타임 확인 (정적 판정 금지 — 절대규칙 2)
```

2) 는 스크린샷 전량을 다시 도므로 수확이 커지면 느리다. 필요하면 새 `win_*` 만
넘겨도 되지만, 그때는 3) 의 hits 집계가 새 판만 반영한다는 점을 감안할 것
(정확한 표를 원하면 전량으로 돌린다).

2. **`{%s}が仲間に加わった`** — 코퍼스에는 캐릭터별 하드코딩판만 있는데

   화면 문자열과 안 맞는다(§4g 발견 4의 재발).
3. **`{%s}には効果がなかった！`** — 코퍼스에는 `効果がなかった！` 조각만 있다.

조사 자동 보정이 신규 이름에서도 정상 동작한다(실측 출력):
`패밀리어는１１피해!` · `패밀리어가나타났다!` · `리아나가 동료가 되었다` ·
`리아나에게는 효과가 없었다!`

## 5. 구현 설계

### 5.1 레코드 경계 판정

문자를 누적하다가 언제 "한 문장이 끝났다"고 볼 것인가.

- 1차: **프레임 경계** — 같은 프레임에 연속 출력된 문자를 한 덩어리로 본다.
- 2차: **원문 사전 매칭** — 누적 버퍼가 `script_sheet.tsv` 의 원문과
  접두 일치하면 그 레코드로 확정한다 (fail-closed: 정확 일치만 채택).
- 타자기식 점진 출력이면 버퍼가 자라면서 매칭이 갱신되므로 자연스럽게 따라간다.

### 5.2 창 위치·색 — **자동 보정 (2026-08-30 실측 확립)**

손으로 재지 않는다. 게임 창은 **단일 플랫 색 직사각형**이므로 스크린샷에서
연결 성분으로 자동 추출된다. 도구 = `tools/build_overlay_rects.py`.

실측 예 (`v2_f03000.png`, 352×234):

| 창 | 배경색 | rect | 글자 영역 | 여백 |
| --- | --- | --- | --- | --- |
| 대사창 | `#006D00` | (18,144) 316×60 | (32,152) 250×43 | L14 T8 |
| 선택지창 | `#006D00` | (18,96) 60×44 | (26,102) 40×29 | L8 T6 |

- 두 창의 rect 는 f2500·f3000 프레임에서 **완전히 동일** — 클래스별로 안정적이다.
- 채움률 0.93 = 글자가 낸 구멍. 이 값이 창 판별의 신호다.
- **덮는 색은 검정이 아니라 창의 실제 배경색**을 쓴다. 프로브 v3 의 검은 박스는
  렌더 가능 여부만 본 테스트 사각형이지 설계가 아니었다.

**팔레트 변화 대응**: `VCEPalette` 메모리 도메인이 존재한다(v4 실측). 색을
하드코딩하지 말고 런타임에 팔레트에서 읽어 쓴다 — 지역·시간대에 따라 창 색이
바뀌어도 자동으로 따라간다.

**수확 워크플로**: `run_z11_harvest.cmd` 로 평소처럼 플레이하면
`tools/harvest_z11_windows.lua` 가 텍스트가 그려질 때마다 **깨끗한 스크린샷 +
원문 SJIS + 스트림 포인터**를 자동 기록한다. 그 산출물을
`build_overlay_rects.py` 에 넣으면 클래스별 색·rect·글자 원점 표가 나온다.
사람이 하는 일은 `class` 열에 이름을 적는 것뿐이다.

### 5.2b 수확 361장 전수 결과 — **정적 rect 표만으로는 부족하다 (2026-08-30)**

`build_overlay_rects.py` 를 수확 360장에 전수 적용: **고유 rect 81개
(3회 이상 등장 = 실사용 47개 / 1~2회 잡음 34개)**.

| 배경색 | 검출 | 고유 rect | 정체 |
| --- | ---: | ---: | --- |
| `#006D00` | 694 | 25 | 대사 계열 — 전투 메시지창·필드 대사창·초상화 대사창·선택지 |
| `#6D9191` | 257 | 25 | 메뉴 계열 — 메인 메뉴·상태창·소형 메뉴 박스 |
| `#002424` | 40 | 3 | 보조 창 |
| `#FFFFFF` | 58 | 21 | 하이라이트/오탐 추정 — 선별 필요 |

확인된 창 예: 전투 상태창 `(2,0) 348×44`(240회, HP 표시) / 전투·필드
대사창 `(2,160) 348×60`(185회) / 초상화 대사창 `(18,144) 316×60`(50회).

**⚠ 두 가지가 정적 표 설계를 깬다:**

1. **선택지 창은 내용에 따라 폭이 변한다** — 같은 클래스가
   `(2,160) 92×60`(40회)·`(2,160) 60×60`(20회) 등으로 나온다.
   옵션 문자열 길이에 맞춰 게임이 창을 만든다.
2. **해상도가 2종이다** — 게임플레이 `352×234`, 부팅 `256×234`.
   rect 는 반드시 해상도와 함께 저장해야 한다.

→ **결론: 정적 rect 표는 고정 창(전투 상태·대사창)에만 쓰고, 가변 창은
런타임 검출로 간다.** 근거는 확보돼 있다 — `VRAM1`·`VCEPalette` 도메인이
존재하고(v4 실측), 훅 비용이 사실상 0이라 프레임당 BAT 스캔 여유가 있다
(239.6 fps = 실시간 4배). 창 배경 타일이 화면 어디에 깔려 있는지 BAT 에서
읽으면 rect 를 매 프레임 그대로 얻는다.

→ 이 방식이면 **클래스별 수작업 라벨링 자체가 대부분 불필요**해진다.
정적 표는 폴백으로만 남긴다.

### 5.2a 레코드 식별 — 스트림 포인터 (v4 실측)

`$967E` 시점에 제로페이지에서 **스트림 포인터가 그대로 보인다**:

- `zp $54/$55` = 기본 스트림 (v4 에서 `65 66 67 68 69 6A` 로 +1 연속 관측)
- `zp $52/$53` = 초상화·메모 스트림

→ 문자열 접두 매칭(§5.1)보다 **HANDOFF §6 의 source key 산식**으로 식별하는 쪽이
견고하다. 문자열 매칭은 폴백으로 남긴다.

**글자 위치**: 제로페이지에 깨끗한 화면 커서는 없었다(zp 전수 덤프). `$FA/$FB` 도
글리프 스테이징 버퍼다(P5). 따라서 배치는 **창 rect + 글자 원점 + 12px 격자**로
계산한다 — 위 자동 추출이 원점과 여백을 주므로 추가 실측은 필요 없다.
